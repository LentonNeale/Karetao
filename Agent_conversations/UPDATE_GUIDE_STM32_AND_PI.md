# Updating the STM32 and Raspberry Pi with the TIME_SYNC Measurement Work

**Audience:** whoever is deploying the TIME_SYNC characterisation changes (commit `2ab115b` and later)
onto an already-provisioned STM32 board and Raspberry Pi. This guide assumes both devices are already
bring-up-complete per `RaspberryPi_Sensor_Hub/Documentation/RASPBERRY_PI_BRINGUP_V1.md` and
`Arm_Sensor_Hub/Documentation/development.md`. It only covers pulling and applying *this* update, not
first-time provisioning.

**Scope:** this update touches STM32 firmware (`Arm_Sensor_Hub/App/**`), Pi-side Python
(`RaspberryPi_Sensor_Hub/src/spi/**`, `RaspberryPi_Sensor_Hub/tools/**`), and documentation only. It does
not change SPI wiring, GPIO assignment, or cloud-init provisioning — no re-imaging is needed.

---

## Prerequisites

- STM32 build host with CMake ≥ 3.22, Ninja, and `st-flash` (or ST-Link tooling), connected to the board
  over SWD. This can be your dev workstation or the Pi itself, as long as the packages below are on it —
  the `HostTests` preset only needs the native `gcc`/`g++`, but `Debug`/`Release` need the ARM cross
  toolchain. On Debian/Ubuntu (including Raspberry Pi OS):

  ```bash
  sudo apt update
  sudo apt install -y gcc-arm-none-eabi libstdc++-arm-none-eabi-newlib gdb-multiarch
  which arm-none-eabi-gcc arm-none-eabi-g++ st-flash gdb-multiarch
  ```

  Note there is no `arm-none-eabi-gdb` package on Ubuntu — `gdb-multiarch` is the substitute used for SWD
  debugging in Part A5 below.
- Raspberry Pi already provisioned and reachable over SSH, with the Karetao repository cloned to `~/karetao`
  (see bringup guide Part D1).
- Both machines have network access to `https://github.com/LentonNeale/Karetao.git` (origin), or the update
  is being carried in on removable media.

## Part A — Update the STM32 firmware

Run these steps on the machine you use to build and flash the STM32, not on the Pi (unless that machine also
hosts the ARM toolchain and ST-Link).

### A1. Pull the update

```bash
cd /path/to/karetao        # your existing clone
git fetch origin
git checkout main
git pull origin main
git log -1 --oneline        # confirm you're on 2ab115b or later
```

If you have local uncommitted changes, stash them first (`git stash`) — do not discard them blindly.

### A2. Validate with host tests before touching the board

This is the fast, hardware-free check. It catches protocol/struct regressions before you spend time flashing.

```bash
cd Arm_Sensor_Hub
cmake --preset HostTests
cmake --build --preset HostTests
ctest --preset HostTests --output-on-failure
```

Expect both `sprint1_protocol_tests` and `service_smoke_tests` to pass. Do not proceed to flashing if either
fails — the debug mirrors added in this update (`TimeService_SyncDebugMirror`,
`SpiSlaveService_TimingMirror`) are exercised here.

### A3. Build the firmware

```bash
cmake --preset Debug
cmake --build --preset Debug
```

Use `Debug` (not `Release`) if you intend to read the debug mirrors over SWD afterward — the SWD readout
procedure in `Arm_Sensor_Hub/Documentation/SWD_READOUT_PROCEDURES.md` assumes a Debug build with symbols.

The build produces `build/Debug/Arm_Sensor_Hub.elf`, `.bin`, and `.hex` (the `.bin`/`.hex` are generated by
an `objcopy` post-build step so `st-flash` has something it can consume — see
`Arm_Sensor_Hub/CMakeLists.txt`).

### A4. Flash the board

Confirm the board is connected over SWD (ST-Link V2 or compatible) before running this — flashing is not
reversible mid-write, and interrupting it can leave the board unbootable.

```bash
st-flash write build/Debug/Arm_Sensor_Hub.bin 0x08000000
```

`0x08000000` is the STM32F405's internal flash base address. If your ST-Link tooling reports a mismatch
(wrong chip ID, no connection), stop and check the SWD cable and power before retrying — do not re-run the
flash blindly.

### A5. Verify the board booted

Power-cycle or reset the board, then either:

- Watch for the usual boot behaviour (heartbeat LED, CAN/SPI activity) you already use as a sanity check, or
- Attach GDB per `Arm_Sensor_Hub/Documentation/SWD_READOUT_PROCEDURES.md` and confirm
  `g_time_sync_dbg` and `g_spi_timing_dbg` exist as symbols. This needs two terminals: OpenOCD stays
  running in the first as the SWD server; `gdb-multiarch` connects to it from the second.

  Terminal 1 — start the OpenOCD server and leave it running:

  ```bash
  cd Arm_Sensor_Hub
  openocd -f interface/stlink-v2.cfg -f target/stm32f4x.cfg
  ```

  Terminal 2 — launch gdb against the ELF (from the same `Arm_Sensor_Hub` directory, since the path below
  is relative), then type the commands one at a time at the `(gdb)` prompt it gives you — do not paste the
  `(gdb)` prefix itself, that's gdb's prompt, not something you type:

  ```bash
  cd Arm_Sensor_Hub
  gdb-multiarch build/Debug/Arm_Sensor_Hub.elf
  ```
  ```
  target remote localhost:3333
  print &g_time_sync_dbg
  print &g_spi_timing_dbg
  ```

  If `target remote localhost:3333` refuses the connection, OpenOCD (terminal 1) isn't running yet or
  hasn't finished attaching to the board — check its output there before retrying.

Both `print` commands should resolve to addresses in RAM (around `0x2000xxxx`), not "No symbol in current
context."

## Part B — Update the Raspberry Pi

Run these on the Pi itself (SSH in as the `robot` user, or whichever account owns the clone).

### B1. Pull the update

```bash
ssh robot@<pi-host>
cd ~/karetao
git fetch origin
git checkout main
git pull origin main
git log -1 --oneline        # confirm you're on 2ab115b or later
```

### B2. Run the Pi-side unit tests

No build step is required — the SPI scaffold under `RaspberryPi_Sensor_Hub/src/spi/` is plain Python and
picked up directly. Just confirm the update didn't break anything:

```bash
python3 -m unittest discover -s RaspberryPi_Sensor_Hub/tests/spi -p 'test_*.py' -v
```

Expect all tests to pass (155+ at the time of this update, spanning protocol encode/decode, TIME_SYNC
session/offset math, CSV logging and analysis, DATA_READY latency analysis, measurement reports, and the
validation-claims tests).

### B3. Rebuild the ROS workspace only if it's out of date

If you have a `colcon` workspace with `RaspberryPi_Sensor_Hub` symlinked in
(`~/karetao_ws/src/RaspberryPi_Sensor_Hub -> ~/karetao/RaspberryPi_Sensor_Hub`), the symlink means the new
Python files are already visible without a rebuild. Re-run `colcon build` only if a ROS package manifest
changed (it did not in this update) or if you're unsure:

```bash
cd ~/karetao_ws
colcon build --symlink-install
```

This update does not add or modify any ROS package files, so this step can usually be skipped.

### B4. Confirm the new tools are present and runnable

```bash
cd ~/karetao/RaspberryPi_Sensor_Hub
python3 tools/spi_time_sync_probe.py --help
python3 tools/spi_measurement_harness.py --help
```

Both should print their `argparse` help text without import errors. If you get a `ModuleNotFoundError`,
confirm you're running from inside `RaspberryPi_Sensor_Hub` (or that its `src/` is reachable) — both scripts
add their own `src/` to `sys.path` at the top, so running them via their file path (not `python -m`) is the
supported invocation.

## Part C — End-to-end check with the board attached

With the STM32 flashed (Part A) and the Pi updated (Part B), and the SPI/DATA_READY harness wired per
`SYS-SPI-004` (20–30 cm cable):

```bash
cd ~/karetao/RaspberryPi_Sensor_Hub
python3 tools/spi_link_probe.py --data-ready --transactions 10
```

This is the existing link-health probe (unchanged by this update) — use it first to confirm the SPI link
itself is still alive after reflashing, before running the new TIME_SYNC probe. Look for `VERDICT: firmware
answered GET_VERSION. The link works.`

Then run a short TIME_SYNC measurement:

```bash
python3 tools/spi_time_sync_probe.py --data-ready --transactions 20 --verbose
```

**Note on current scope:** as documented in
`Documentation/05_VERIFICATION/TIME_SYNC_VALIDATION.md`, the STM32 firmware does not yet implement a
TIME_SYNC responder, so TIME_SYNC requests will currently be NACKed or timeout — this is a known,
tracked gap (Gap 5), not a failure of this update. The probe, session math, and analysis tooling are ready
for when that firmware support lands; today's run is a smoke test that the encode/send/decode path doesn't
crash, not a synchronization-accuracy measurement.

For the fuller multi-session repeatability run and SWD correlation procedure once TIME_SYNC responses are
available, see `Documentation/05_VERIFICATION/TIME_SYNC_VALIDATION.md` ("SWD Readout Integration") and
`Arm_Sensor_Hub/Documentation/SWD_READOUT_PROCEDURES.md`.

## Rollback

If the update causes a regression on hardware:

**STM32:**
```bash
cd Arm_Sensor_Hub
git log --oneline -5                 # find the last known-good commit
git checkout <previous-commit> -- .
cmake --build --preset Debug
st-flash write build/Debug/Arm_Sensor_Hub.bin 0x08000000
```

**Raspberry Pi:**
```bash
cd ~/karetao
git checkout <previous-commit>
```

Prefer checking out a specific known-good commit over `git reset --hard`, so you don't discard any local
diagnostic notes you may have added outside version control.
