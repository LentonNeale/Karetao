## 1. Background: the efficiency test

`tests/efficiency/` is a recurring test that measures how agents spend tokens on real User requests, and asks the orchestrator for **deterministic Python tools, hooks and shared files** that would do the same work more cheaply.

1. `extract_usage.py` runs **locally** in a project. It turns Claude Code transcripts into an anonymised digest: counts only, no conversation text, stable pattern ids.
2. The orchestrator follows `tests/efficiency/CONTEXT.md` and writes `results/proposals.json` and `results/summary.md`.
3. `check_proposals.py` validates the admission rules (Python-only, concrete input/output contracts, deterministic, cites digest evidence, generic) and ranks the proposals by estimated tokens per week.

Run it with `workspace/tests/efficiency/run.sh` from a project root. It cost $1.00 on Opus. Run 1 produced 9 of 9 valid proposals and 7 recorded rejections.

## 2. The key finding

The digest covered 57 sessions over 9 days (14 interactive, 43 headless). **Context re-reads dominate cost.** Interactive sessions re-read about **194k tokens of context per message**: 773M cache-read tokens over 3,989 messages, against roughly 1M tokens of tool output in total. So:

- **Removing a sequential tool turn saves far more than shrinking a tool result.** One turn is about 19.4k price-weighted tokens (194k × 0.1 cache-read weight).
- A large result costs its size again on every later turn. The test assumes ×3, pending better data (WP10).

Build to remove turns first and cap sizes second.

## 3. Work packages

Each work package is **one PR** into `main`. Scripts use Python 3.10+ and the standard library only, calling `git`, `gh` or `jq` as subprocesses where needed. Tests use `unittest` under `tests/tools/test_<name>.py` and must include the failure cases listed. Every tool must be generic: project specifics come from `icm-project/` or arguments, never from constants.

**The exact contracts are in the proposal records** and are the source of truth: `input`, `output`, `trigger`, `test_plan` and `risks` for each. They are in `reports/efficiency-tooling/proposals-run1.json` next to this report (generalised wording, same contracts). Summaries:

- **WP1 file-map.**
  - Input: `file_map.py --root <dir> --out <file> [--exclude <glob>]...`, with the file list from `git ls-files`.
  - Output: one Markdown table per top-level folder, with columns `path | lines | est_tokens | outline` (the first 5 headings or top-level definitions). A header line carries the generating commit SHA. Output is byte-identical on re-run; exit 1 outside git.
  - Regenerated by a SessionStart hook (see WP11). Gitignored, so no project content enters the shared repo.
- **WP2 section.**
  - Input: `section.py <file> --outline | --heading <text> | --line <n> | --match <regex> [--max 3]`, for `.md`, `.py` and `.c`/`.h`/`.cpp`/`.hpp` files.
  - Output: numbered lines of the enclosing section or function, at most 400 lines with a truncation marker. Exit codes: 0 found, 1 no match, 2 unsupported file.
  - C brace matching must ignore comments and strings.
- **WP3 repo-state.**
  - Input: `repo_state.py [--log N] [--base <ref>] [--json]`.
  - Output: branch, upstream ahead/behind, short status, stash count, last N commits and diffstat, plus a `state` field for merge, rebase or cherry-pick in progress.
- **WP4 reread-guard.** Denies a Read whose file hash and range are unchanged since an earlier Read in the same session, with a one-line reason. State is kept per session in `${TMPDIR}` and cleared on compaction (PreCompact, and SessionStart with source `compact` or `clear`). **Fails open** on any error.
- **WP5 edit-context.** After an Edit, returns the edited region with 3 lines of context and line numbers (at most 40 lines) as `additionalContext`. It's on probation: remove it if the Edit→Read rate doesn't halve in the next digest.
- **WP6 test-summary.**
  - Input: `test_summary.py [--max-failures 3] [--excerpt-lines 30] -- <command>`.
  - Output: one `PASS|FAIL runner passed= failed= … log=<path>` line plus the first failure excerpts. The exit code equals the wrapped command's. If parsing fails, it falls back to the log tail.
  - `build-runner` should use it (update `agents/build-runner.md`).
- **WP7 grep-cap.** Rewrites only single, unpiped `grep -r`/`rg` commands that lack `-l`, `-c` or `-m`, capping output at 60 lines plus per-file match counts. It preserves grep's exit status.
- **WP8 read-size-guard.** For a Read with no offset or limit of a file over about 4k tokens (threshold set by `ICM_READ_CAP_TOKENS`), it sets `limit: 200` and adds WP2's outline with line ranges.
- **WP9 md-table-query.**
  - Input: `md_table.py <file> [--table <n or heading>] [--where col=regex]... [--columns a,b] [--json]`.
  - Output: the matching rows with the original header. Exit codes: 0 rows found, 1 none, 2 unknown column or table.

## 4. Engineering rules

- Follow `CLAUDE.md` and the stage contracts.
  - **Delegation:** implement well-specified work packages through `python-dev` (Haiku), which runs its Step 0 escalation gate; the orchestrator reviews each diff. Anything that touches hook wiring into `.claude/settings.json` is orchestrator work.
  - **Hooks must fail open:** any exception means no output and exit 0. They must stay under 200 ms, and never block a tool call except as their contract describes.
- **Determinism:** the same input gives the same output. No model calls inside tools or hooks.
- **No project content in the shared repo.** Generated files (`shared/file-map.md`, state files) are gitignored, and test fixtures are synthetic.
- **Don't touch GUI files** (`gui/**`, and the `scripts/icmlib.py`, `review.py`, `helper.py` and `stage_status.py` coming from the `icm-gui-prototype` branch). A separate agent owns them. The new files in this report don't overlap with them.
- **One PR per work package into `main`.** Each PR: tests pass (`python3 -m unittest discover -s tests/tools` and `-s tests/efficiency`), a description with the contract and test evidence, and no merge without the User's approval.

## 5. Acceptance: how the team knows it worked

1. **Contracts:** each work package's unit tests cover every case in its `test_plan`, including the failure cases.
2. **Measurement:** after WP1–WP9 and WP11 are merged and enabled in a project for about a week, re-run `tests/efficiency/run.sh` there. Compare the new digest with run 1:
   - `tokens_by_mode.interactive.cache_read` per message should fall;
   - the targeted patterns (B1/B2/B4-B7 shapes, the S5/S7/S14/S18/S22 sequences, R-series re-reads) should drop;
   - the new tools should appear in the tool counts.
3. Report the comparison as `tests/efficiency/results/summary.md` in that project. Promote only generic conclusions back into this report.
